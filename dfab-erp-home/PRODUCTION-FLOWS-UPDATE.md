# DFAB OneERP — production-flow update

23 November 2026. This folder updates the previous GitHub CI corrected project. The original folder is retained separately. No production database changes or deployment were performed during development.

## What changed

- All 58 transaction schemas now use the connected inline editor with the existing DFAB theme. Header fields retain the inspected reference labels. Dense headers are divided into short field pages. Product lines, charges, taxes, totals, files, inspection, operations and assignment have separate sections. Create forms remain inside the screen. Fetch alone uses a selection dialog.
- Fetch shows eligible released sources and per-line source quantity, already fetched quantity, pending quantity and editable Fetch Qty. Saved drafts reserve their quantities. Replacing existing lines requires confirmation. A concurrent change is rejected rather than overwriting another user's work.
- Draft, submission, approval, rejection and next-task actions persist headers, lines, the original registers, invoice details and lineage together. Existing module permissions remain enforced. Document numbers are generated by the database.
- Manufacturing and Labour Job Work have their own SOP branches. Inward QC gates production; route operation completion and required operation QC gate output; outward QC gates dispatch; dispatch gates invoicing. Payment allocations include cash, TDS and LD. Closure requires the linked quantities delivered, invoiced and fully settled.
- Reorder Planning creates a normal draft Purchase Indent using the same atomic transaction save. Existing extension policies, follow-up notes, stock calculations, duplicate prevention and statement links remain connected.
- Registers, reports, stock and receivables consume the saved multi-line records. Vendor Payment History has the vendor title/filter. Pending Approvals opens the selected transaction directly. Published Admin workflow edges and field mappings are retained; physical release gates still apply.
- Invoice Workflow includes Zoho SMTP email for saved, approved invoices. The server reads the invoice from the database and sends an escaped HTML invoice copy and HTML attachment. Browser Print remains available. This is not a signed PDF or GST IRN integration.

Masters, menu structure, login animation, authentication/session handling, Admin Control, reports and the separate ERP Extensions section retain their existing scope and theme. The regression suite checks those surfaces. Historical documentation remains in this folder; this file describes the current release.

## Existing records

Existing raw register rows remain readable. Their original totals, headers, dates, files and reference values are retained. If item details or dates are missing, the system marks the record for reconciliation. It does not invent dates or tax amounts. Before releasing such a record, open Edit, verify its original item lines and date and confirm the reconciliation checkbox. A paid invoice cannot be silently edited. Downstream source reservations and stock checks apply to newly committed records.

## Required database update

1. Back up Supabase and first apply this release to a staging copy.
2. Ensure the existing baseline migrations in README.md are installed, including `ERP_QA_EXTENSIONS_UPDATE.sql`.
3. Run **`supabase/ERP_PRODUCTION_FLOWS_UPDATE.sql`** in the Supabase SQL Editor. It combines `DFAB_PROCESS_UPGRADE.sql`, `ERP_PRODUCTION_PROCESS_CONTROLS.sql` and `ERP_ZOHO_INVOICE_EMAIL.sql` in that order. Use the bundle or those three individual files, not both. It adds guarded RPCs, module mappings, document numbering and private email jobs. It does not delete existing transaction records.
4. Run `npm ci` and `npm run verify`, then deploy the frontend. Keep the existing Supabase project URL and publishable key. Never put service-role or SMTP secrets in a VITE variable.
5. In staging, sign in with an administrator and a restricted staff account and check one transaction, approval, Fetch, report and payment against the migrated data before production deployment.

Deploying the frontend alone is insufficient: atomic saves require the new SQL. A frontend rollback should use the previous folder with its matching database integration; retain the database backup. New guardrails intentionally reject malformed or incomplete physical releases.

## Zoho email setup

Email is optional until configured. ERP transactions, Fetch, reports and payments do not depend on SMTP.

Configure these **Supabase Edge Function secrets**, using your Zoho account's actual data centre and SMTP settings:

| Secret | Value |
| --- | --- |
| `ERP_ALLOWED_ORIGINS` | Exact frontend origins, comma separated; for example `https://erp-lyart-beta.vercel.app,http://localhost:5173` |
| `ZOHO_SMTP_HOST` | Your Zoho SMTP host, for example `smtppro.zoho.in`; confirm in your Zoho account |
| `ZOHO_SMTP_USER` | Full sender mailbox address |
| `ZOHO_SMTP_PASSWORD` | Zoho SMTP/app password stored only as a server secret |
| `ZOHO_FROM_EMAIL` | Authorized sender address, normally the same mailbox |

`SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` are standard server-side Supabase function environment values. Keep the existing `erp-admin-invite` deployment unchanged.

From this folder, using the Supabase CLI connected to your project, deploy:

```sh
supabase functions deploy erp-invoice-email --project-ref YOUR_PROJECT_REF --no-verify-jwt
```

This function verifies every user token with Supabase Auth inside its handler and checks invoice permissions. The deployment flag avoids the separate legacy gateway JWT check rejecting newer project keys; it does not remove the handler's sign-in requirement. See https://supabase.com/kb/troubleshooting/edge-function-401-error-response .

Use the CLI's secret manager or dashboard to configure credentials; do not commit them. The function uses TLS SMTP on port 465, validates the ERP session and invoice export permission, and reads the stored approved invoice. Its delivery job is idempotent for the same request ID. A timeout is recorded as unknown; check Zoho Sent before deliberately sending another request. The function does not automatically retry an uncertain delivery. Hourly limits apply per ERP user.

After deployment, open a saved approved Sales Invoice → Workflow, enter a test recipient, send once and confirm delivery in Zoho and the recipient mailbox. This live test remains required because SMTP credentials were not supplied during development. Setup reference: https://www.zoho.com/mail/help/zoho-smtp.html .

## Deferred integration

GST e-invoicing remains disabled because the old ERP's provider/credential configuration was unavailable. IRN/Ack fields remain reference fields; the UI does not claim an IRN has been issued. No external service credentials or customer emails were used in automated QA.

## Verification

See `QA-PRODUCTION-FLOWS.md` for the recorded results and scope. Browser tests use isolated authenticated fixtures; SQL tests run the actual migrations and guarded RPCs in an isolated PostgreSQL runtime. They do not modify customer production data.

```sh
npm ci
npm run verify
npx playwright install chromium
npm run test:browser
npm install --no-save --package-lock=false @electric-sql/pglite
npm run test:sql
npm audit --omit=dev --audit-level=high
```

For an already installed standalone PGlite, set `ERP_PGLITE_DIR` to its `dist` directory instead of the optional install. For a nonstandard Chromium binary set `ERP_CHROMIUM_PATH`. The configured typecheck covers the existing utility JavaScript module; lint, unit tests, browser tests and builds cover the changed application. Live SMTP, production Supabase/Vercel configuration and production-data reconciliation remain deployment acceptance checks.
